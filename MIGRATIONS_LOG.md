# Migration history (Supabase project bgbcyncpdfnsrhvunzkv)

The base schema and RLS policies are in `supabase_001_schema_and_rls.sql`.
Everything after that was applied directly to the live database via Supabase
migrations (not re-exported to a local .sql file, to avoid drift between two
sources of truth). For reference, the migrations applied so far, in order:

1. `001_schema_and_rls` — base tables (organizations, memberships, transactions) + RLS
2. `002_harden_functions` / `003_harden_functions_explicit_roles` — function hardening
3. `fix_org_select_chicken_egg` — fixed first-login org creation being blocked by RLS
4. `add_partner_invites` — `invites` table, `accept_invite()` RPC, RLS
5. `fix_accept_invite_column_ambiguity_v2` — PL/pgSQL OUT-parameter fix
6. `harden_accept_invite_display_name_fallback`
7. `prevent_duplicate_pending_delete_requests` — unique index on `delete_requests`
8. `setup_receipts_storage` — private `receipts` Storage bucket + RLS policies
9. `add_locked_months` — `locked_months` table + `check_month_not_locked` trigger
10. `harden_check_month_not_locked` — locked down the trigger function (search_path, revoked direct EXECUTE)
11. `add_org_tax_rate` — `organizations.tax_rate` column (default 10), editable by the owner only (existing `org_update` RLS policy already covers it)
12. `add_projects_delete_policy` — `projects` table had INSERT/SELECT policies but no DELETE policy, so deletes silently no-op'd (HTTP 200, 0 rows affected). Added `projects_delete` policy: `FOR DELETE USING (is_org_owner(org_id))`.
13. `add_partner_names_to_organizations` — added `partner_a_name` / `partner_b_name` columns to `organizations`. **Superseded by #15 below** — reverted once the design changed from "owner-only names" to "each partner edits their own name".
14. `enable_realtime_on_transactions` — `ALTER PUBLICATION supabase_realtime ADD TABLE transactions;`. The publication was empty before this, so `postgres_changes` subscriptions on `transactions` silently received nothing; a transaction added by one partner only appeared for the other after a manual page refresh.
15. `revert_partner_names_on_organizations` — dropped `organizations.partner_a_name` / `partner_b_name` (see #13).
16. `allow_self_update_membership_display_name` — final partner-name design: each partner edits only their own name, stored in `memberships.display_name`. Adds a second, more permissive UPDATE policy (`membership_update_self`, `USING (user_id = auth.uid())`) alongside the existing owner-only policy — Postgres RLS policies are OR'd together, so this only *adds* permission. A `BEFORE UPDATE` trigger (`enforce_membership_self_update()` / `membership_self_update_guard`) compares `OLD` vs `NEW` and blocks non-owners from changing `role`, `share_percent`, `org_id`, or `user_id`, while still allowing them to change their own `display_name`. RLS `USING`/`WITH CHECK` clauses can't compare old-vs-new column values directly, hence the trigger.

Note (2026-10-12): migrations applied live between #16 and the entry below (`add_projects_table` … `organizations_draw_mode`, 27 in total) were not logged here; `supabase list_migrations` is the authoritative list.

- `add_projects_contract_amount` (2026-10-12) — nullable `projects.contract_amount numeric(12,2)` with `CHECK (> 0)`. Shown on the project card as contract · received · still owed (`SBCalc.contractStatus`, verified income only). SQL: `supabase/migrations/20261012_add_projects_contract_amount.sql`. Apply before deploying the app change.
- `transactions_partner_approval` (2026-10-12) — `transactions.approved_by/approved_at`; `approve_transaction(p_tx)` RPC (never your own row); `tx_approval_guard` trigger (clients cannot set approval; editing content clears it; single-member orgs auto-approve); existing rows backfilled as approved at `created_at`; helper `org_member_count()`. SQL: `supabase/migrations/20261012_transactions_partner_approval.sql`. Applied to prod 2026-10-12 before the app change; rules checked in a rolled-back transaction (10/10).
- `mark_transaction_paid` (2026-10-12) — RPC that sets status pending → verified for a row of the caller's own org. Fixes "Mark as paid" by a member on the owner's row (was a silent no-op under RLS `tx_update`). Applied to prod 2026-10-12; checked in a rolled-back transaction (bug reproduced, fixed, approval untouched, foreign org refused). SQL: `supabase/migrations/20261012_mark_transaction_paid.sql`.
- `tx_guard_immutable_owner_org` (2026-11-21) — `tx_approval_guard` now rejects client UPDATEs that change `org_id` or `created_by_user_id`. Closes an approval bypass found in the 2026-11-21 security audit: the owner could set `created_by_user_id` to the partner and then approve the row himself. Moving a row to another org was already refused by RLS; the trigger now refuses it too. The app never changes these columns. Tested on a local Postgres copy of the schema (Supabase branching needs Pro): exploit reproduced before, blocked after, 5 regression checks green. Applied to prod 2026-11-21. SQL: `supabase/migrations/20261121_tx_guard_immutable_owner_org.sql`, rollback: `…rollback.sql`.
- `receipts` bucket limits (2026-11-21, `execute_sql`, not a schema migration) — `storage.buckets.receipts`: `file_size_limit = 15728640` (15 MB), `allowed_mime_types = {image/jpeg,image/png,image/webp,image/heic,image/heif,image/gif,application/pdf}`. HEIC/GIF kept because `compressReceipt` returns the original file when it cannot re-encode. Largest existing object was 7.7 MB. Rollback: `update storage.buckets set file_size_limit = null, allowed_mime_types = null where id = 'receipts';`
- `reject_transaction` (2026-10-18) — RPC: a member who did NOT create an unapproved row can set it to `rejected` (stops counting). Own rows, approved rows and other orgs are refused. Raises P0001 when nothing changed (approved/rejected meanwhile), so the UI never reports a silent no-op. Same migration: `approve_transaction` no longer approves a rejected row. Month lock still applies. Tested in a rolled-back transaction on prod data (10/10 cases). Button «Reject» in the «To approve» card.
- `tx_guard_rejected_is_final` (2026-11-22) — `tx_approval_guard`: a client cannot change `status` away from `rejected`. Before, the owner could pick «verified» in the edit form and silently undo the partner's rejection. A rejected row can still be edited (stays rejected) or deleted. Tested on a local Postgres copy: un-reject FAIL before / PASS after, 13 other checks green both ways. Apply together with `reject_transaction`, before merging the app change. SQL: `supabase/migrations/20261122_tx_guard_rejected_is_final.sql`, rollback: `…rollback.sql`.
- `share_periods` (2026-11-22) — partner shares from a date. Before, `memberships.share_percent` was one number applied to the whole history: changing 50/50 → 60/40 re-split every past month, locked months included. New table `share_periods(org_id, effective_from, share_a)` (members read; no client writes), RPC `set_partner_shares(p_org, p_share_a, p_from)` (owner only; start date not inside a locked month; first change stores the old shares as a base period from 1900-01-01; later periods from `p_from` on are replaced; keeps `memberships.share_percent` = shares in force today), trigger `membership_share_via_rpc_only` (a direct UPDATE of `share_percent` is refused). App: `SBCalc.computeSplitByPeriods` splits each period with its own shares and sums. Orgs without rows keep the old single split. Tested on a local Postgres copy: 15/15 (S3 fails with the trigger removed). Apply before deploying the app change. SQL: `supabase/migrations/20261122_share_periods.sql`, rollback: `…rollback.sql` (deploy the previous app first).
- `tax_periods` (2026-11-22) — tax reserve rate from a date, same pattern as `share_periods`. Before, `organizations.tax_rate` applied to the whole history: 10 % → 19 % re-counted every past month's reserve. Table `tax_periods(org_id, effective_from, tax_rate)`, RPC `set_tax_rate(p_org, p_rate, p_from)` (owner only, not inside a locked month, keeps `organizations.tax_rate` = rate in force today), trigger `org_tax_via_rpc_only`. App: `SBCalc.computeSplitByPeriods` cuts the history at every share or tax change. Local Postgres: 12/12 (T3 fails with the trigger removed). SQL: `supabase/migrations/20261122_tax_periods.sql`, rollback: `…rollback.sql` (deploy the previous app first).
- `admin_views_v2` (2026-11-22) — back-office views: income/expense/draw totals in `v_admin_org_health` count verified rows only (as the app); new columns `tx_rejected`, `tx_awaiting_approval`, `income/expense/draw_pending`, `is_test`.
